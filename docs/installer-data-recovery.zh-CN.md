# 安装数据恢复与错误诊断

基线：`v3.0.7-preview.14` / `a5ee691e`。

## 已证实的代码问题

- 模块 `status` 在存在安装数据选择时返回 `install_data_update_pending`。这是保护状态，不能用“授予 Root 权限”解释；主界面此前丢弃实际异常，所有恢复失败都用同一条 Toast 提示，且长文字被截断。
- HTTP/TCP 批量测速在 View 生命周期结束时会取消，但释放 `runningTest` 的另一个 View 协程也可能被取消，造成后续恢复一直认为测速未结束。现在由父任务完成回调释放标记，时机在全部子任务结束之后；销毁 View 同时关闭批量测速弹窗。
- App 的恢复日志仅保存原备份，没有完成阶段。数据库已提交、末尾模块确认失败时，重试会重复归档和恢复数据库。现在每步成功后使用 AtomicFile 保存进度；确认重试不再重写已提交的数据库，不再依赖订阅取消成功。
- WorkManager 配置指定默认进程 `:bg`，合并 Manifest 中 RemoteWorkManagerService 却没有 process，落在主进程。现在与 RemoteWorkerService 一起配置为 `:bg`，并为取消请求设置 15 秒边界。

## 数据边界

仍按安装器已确认的三种方式处理，完整备份先落盘并校验。新进度仅是 App 私有 `pending.json` 中的 `phase` 字段，旧日志没有该字段时从原来的完整备份流程恢复；不修改备份格式、Room schema 或安装令牌。失败不删除日志或备份，不绕过模块 pending 保护，不自动更改安装数据选择。

App 数据恢复仅由主进程执行。`:bg` 磁贴使用独立 Mutex，无法看到主进程的测速任务；有待处理选择时磁贴只提示打开管理 App，避免两个进程同时修改恢复日志和数据库。普通磁贴连接操作保持原有行为。

阶段依次为 `BACKED_UP`、`MODULE_PREPARED`、`APP_COMMITTED`、`MODULE_FINISHED`。每个操作后持久化阶段，随后才进入下一步；模块确认使用原始令牌。数据库已提交后的重试仅完成剩余模块步骤和界面刷新。操作成功但阶段写盘失败时，仍依靠原有事务/模块幂等机制安全重试。

## 诊断与验证

恢复错误显示完整对话框，日志只记录固定阶段、异常类型链与过滤后的错误代码，不记录异常原文、备份内容、节点或订阅凭据。pending、测速忙、订阅忙、令牌变化分别提示。

新增单元测试覆盖每步失败后的重入、检查点写失败、取消传播与凭据脱敏；仪器测试使用实际导出生成器、AtomicFile 和 Room，验证确认失败后重试不会重复清理数据库，并实际调用订阅取消入口检查服务进程配置。

用户截图已显示超级用户授权开关开启，但尚未提供这次失败的完整异常日志，不能据此断定具体失败阶段，也不能把模拟器测试当成该手机的 Root 恢复成功。

## 优化记录（preview.15 之后）

- **已提交重试跳过备份解析**：`phase >= APP_COMMITTED` 时不再重新解析、重组与校验完整备份，重试只做模块收尾、安装器确认与界面刷新；避免大备份重复解析开销，也避免校验波动阻塞本可完成的收尾。
- **成功后清理陈旧备份**：`pending.json` 删除后，仅保留最近 3 份 `OwnBox_backup_*.json`，其余删除，防止 `module-update-backups` 无限增长。
- **journal 损坏可诊断**：`pending.json` 无法解析、版本号未知或阶段名非法时，抛出 `installer_journal_corrupt` 并显示中英提示，不再陷入无明确原因的 JOURNAL 失败循环。journal 新增 `"v": 1` 版本字段；无该字段的旧记录视为 v1 兼容读取。
- **单次 status 读取**：一次 `prepare` 内最多调用一次模块 `status`，结果复用于安装器选择校验。
- 主进程检查收敛为 `requireMainProcess()`；删除全仓库无引用的 `latestBackup()`。
